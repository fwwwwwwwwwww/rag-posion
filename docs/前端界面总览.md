### 怎么做到的

- 顶栏状态来自 `GET /api/health`，它返回 `ready` / `lazy` / `offline`，
  前端映射成三种颜色与文案（`healthText` / `healthType` / `healthTip`）。

- 侧栏底部来自 `GET /api/agent/status`，返回 `model` / `protocol` / `kb_chunks`。

  是判断"这个模型能不能可靠调用工具"的直接依据。
- **退出登录**会先弹确认框，再调 `POST /api/auth/logout` 清 Cookie，最后跳登录页。

# 第一部分 💬 问答演示（`/chat`）

## 界面长什么样

一个**三栏布局**，从左到右是"提问 → 思考过程 → 结果"：

```
┌─────────────┬──────────────────┬─────────────────────────┐
│ Agent 配置   │ 决策轨迹          │ 模型回答                 │
│             │（模型自主选择）    │                         │
│ 攻击场景 ▾   │                  │ ┌─────────────────────┐ │
│ 问题 ▭▭▭    │ ● 调用工具        │ │ ⚠ Agent 判定证据不足，│ │
│ 工具上限 ─●─ │   query=...      │ │   主动拒答            │ │
│ 会话记忆 ●○  │ ● 工具返回        │ └─────────────────────┘ │
│ [ 发送 ]     │   检索到 5 条片段  │  根据提供的资料……        │
│             │ ● 收束生成        │                         │
│ ─────────    │   基于收集到的证据  ├─────────────────────────┤
│ 模型 xxx     │                  │ 检索依据（红色 = 投毒嫌疑）│
│ 通道 [原生]  │  [3 次工具调用]   │ #1 顽固性高血压应联合用药  │
│ 工具 xxx     │                  │ #2 血压清三疗程根治… 🔴投毒│
│ 会话 abc123  │                  │                         │
└─────────────┴──────────────────┴─────────────────────────┘
```

**左栏「Agent 配置」**：

| 控件 | 说明 |
|---|---|
| 攻击场景下拉 | 7 个场景，标签形如 `[肿瘤科] 上海肺癌治疗哪家医院最权威？`；选中后**自动把问题填进输入框** |
| 问题文本框 | 3 行，可自由改写（不一定用场景自带的问题） |
| 工具上限滑块 | 1–12，控制本次 Agent 最多调用几次工具 |
| 会话记忆开关 | 打开后多轮追问共享上下文；打开时下方出现"清空会话记忆" |
| 发送按钮 | 推理中变成"Agent 推理中…"并禁用 |
| 底部元信息 | 模型名、**工具通道**（`原生 tool_calls` 绿 / `react` 黄）、可用工具列表、当前会话 ID |

**中栏「决策轨迹（模型自主选择）」**——这是整个界面最有价值的一块：

- 右上角标签显示"**N 次工具调用**"；
- 每一步是一张彩色小卡，**颜色区分步骤类型**：
  - 🔵 靛蓝底 = **调用工具**（显示工具名 + 参数键值，等宽字体）
  - 🟢 绿底 = **工具返回**（显示人类可读的结果摘要，如"检索到 5 条片段"）
  - 🟡 黄底 = **收束生成**（说明为什么在这里收尾）
- 空状态提示："发送问题后，这里会实时显示 Agent 调用的工具"。

**右栏**：

- 上「**模型回答**」——若 Agent 主动拒答，顶部出现黄色告警条
  "**Agent 判定证据不足，主动拒答**"，且回答文字变为橙色；
- 下「**检索依据（红色 = 投毒嫌疑）**」——每条显示 `#排名 + 内容`，
  被检测器标记的条目整条标红并挂"投毒嫌疑"红标签。

## 能做什么

1. 选一个攻击场景（或自己写问题）；
2. 调工具上限、决定是否开启会话记忆；
3. 点发送，**看着 Agent 一步步自己决定**调哪个工具、调几次；
4. 拿到回答后，直接在同一页看到"哪些证据被判为投毒嫌疑"；
5. 开启记忆后连续追问（"那它的副作用呢？"），验证它是否继承了上文；
6. 随时清空会话记忆重开一轮。

## 怎么做到的

### （1）前端：SSE 逐帧解析，实时刷新轨迹

问答走的是 **SSE（Server-Sent Events）**，不是普通请求。`api.js` 里的 `sseStream()`
用 `fetch` + `resp.body.getReader()` 拿到流，按 `\n\n` 切帧，再从每帧里正则抽出
`event:` 与 `data:` 两行，`JSON.parse` 后分发：

```js
const frames = buf.split('\n\n')
buf = frames.pop()                    // 最后一段可能不完整，留到下次
for (const frame of frames) {
  const event   = (frame.match(/^event: (.+)$/m) || [])[1]
  const dataLine = (frame.match(/^data: (.+)$/m) || [])[1]
  ...
  if (event === 'error') onError?.(data.message)
  else onEvent?.(event, data)
}
```

`streamAgentChat()` 把它包装成四个语义回调：

| SSE 事件 | 回调 | 界面上的效果 |
|---|---|---|
| `session` | `onSession` | 记录会话 ID（显示在左栏底部） |
| `step` | `onStep` | **往决策轨迹里追加一张卡**（tool_call / tool_result / finalize） |
| `sources` | `onSources` | 渲染检索依据，投毒嫌疑标红 |
| `done` | `onDone` | 填入最终回答、判断是否拒答、刷新 Agent 元信息 |

> 注意 `step` 是**逐步到达**的，所以轨迹是"边跑边长"——
> 这正是"Agent 感"的来源：用户能看见模型在行动，而不是等一个黑箱结果。

### （2）后端：把工作线程里的轨迹事件送回事件循环

Agent 是同步阻塞的（LangGraph + 本地模型推理），所以它跑在 `asyncio.to_thread` 的线程里。
但 SSE 生成器跑在事件循环里——两者需要一座桥：

```python
loop = asyncio.get_running_loop()
queue: asyncio.Queue = asyncio.Queue()

def on_step(event):                       # 工作线程里被调用
    loop.call_soon_threadsafe(queue.put_nowait, event)   # ← 关键：线程安全投递

async def run_agent():
    try:
        return await asyncio.to_thread(agent.run, question, session_id,
                                       None, on_step, max_steps)
    finally:
        loop.call_soon_threadsafe(queue.put_nowait, sentinel)

task = asyncio.create_task(run_agent())
while True:                               # 边跑边推
    item = await queue.get()
    if item is sentinel: break
    yield _sse("step", item)
```

Agent 的 `_emit()` 在每一步决策时调用 `on_step`，于是：

```
Agent 决定调 search_kb
   → agent.py 产生 {"step":1,"type":"tool_call","tool":"search_kb",...}
   → on_step → call_soon_threadsafe → queue
   → SSE 生成器取出 → yield "event: step"
   → 前端 onStep → 轨迹里多一张蓝色卡
```

`on_step` 内部还包了 try/except，**回调异常绝不影响主流程**——
避免前端推送问题把一次正常的推理打断。

### （3）Agent 单例：懒加载 + 双检锁，避免重复初始化

首次请求才构建 Agent（要加载向量库、探测模型工具通道，比较慢），
用 `asyncio.Lock` 做双检，并把构建丢进 `asyncio.to_thread` 以免阻塞事件循环：

```python
async def _ensure_agent():
    if _agent_state["ready"]: return _agent_state["agent"]
    async with _init_lock:
        if _agent_state["ready"]: return _agent_state["agent"]
        agent, count = await asyncio.to_thread(_build_agent)
        _agent_state.update(ready=True, agent=agent, kb_count=count)
    return _agent_state["agent"]
```

### （4）会话记忆：清空按钮背后做了什么

`DELETE /api/agent/session/{id}` 直接操作 LangGraph `MemorySaver` 的内部存储字典，
把包含该 session_id 的键删掉。**为什么需要这个按钮**：MemorySaver 是进程内内存，
不清理的话同一个 session 会一直累积上下文。

### （5）"投毒嫌疑"标签怎么来的

`check_poison` 工具被调用后，判定结果会写进证据的元数据
（`poison_suspect=True`）；最终 `_build_sources()` 把它映射成接口字段，
前端按 `s.poison_suspect` 决定是否标红。

## 完成了什么

- **真实模型端到端跑通**（`qwen3.5:2b` + 5571 chunk 向量库）：
  模型自主串起 `search_kb → check_poison → cross_check` 后收束，
  并在证据不足时回答"知识库中没有足够依据"；

- **投毒可见**：被检测器标记的检索片段在界面上标红，一眼能看出"回答是基于什么给的"；
- **12 项控制流回归 + 5 项接口测试**全过（`tests/test_agent_smoke.py`、`tests/test_agent_api.py`）。

**启动区控件**：

**轨迹区**：三组 **CSS 柱状图**（蓝=召回@k、绿=检出率、红=ASR），
每根柱标注轮次，下方用等宽字体列出数值序列；
再下面是明细表：**轮 / 策略 / 召回@k / 检出率 / 核查通过 / ASR / 判定 / 死在 / 换策略理由**。

界面上的两个颜色约定：

- **检出率 > 0 显示为绿色加粗**——说明防御真的起作用了；
- **ASR 用标签呈现**：`成功`（红）/ `失败`（绿）；
- **判定**用四色标签：`endorsed` 红 / `rejected` 绿 / `mentioned_only` 黄 / `unrelated` 灰。

## 能做什么

1. 选场景 + 选目标防御档 + 设轮数与投放量 → **一键启动攻击战役**；
2. 在"启动"的同时就能看到**攻击者手上有哪些策略、每种针对哪条防线**；
3. 战役跑完后看**攻击轨迹**：第几轮换了什么策略、为什么换、四层指标如何变化、最终死在哪一层；
4. 按界面下方的判读提示，自己判断"这次是攻击没进检索，还是防御拦住了"。

## 怎么做到的

### （1）接口是"提交即返回"，不是"等到跑完"

一次战役少则几分钟、多则几十分钟（本地小模型单次问答 20–47s），
所以 `POST /api/attacks/campaign` 立刻返回 **202**，只回一句"已提交后台执行"：

```python
@router.post("/campaign", response_model=CampaignStarted, status_code=202)
async def start_campaign(req: CampaignRequest):
    with _lock:                                   # 防同一场景重复提交
        if req.attack_index in _running:
            raise HTTPException(status_code=409, detail="该场景的攻击战役已在运行")
        _running.add(req.attack_index)
    threading.Thread(target=_run_campaign_job, args=(req.attack_index, req),
                     daemon=True).start()
    return CampaignStarted(status="started", ...)
```

前端拿到 202 后 `setTimeout(loadIterations, 3000)` 延迟拉一次轨迹——
给后台线程一点时间写出第一轮。

### （2）轨迹从哪来

每轮结束，`attack/campaign.py::_persist()` 把这一轮写进 `attack_iterations` 表
（策略、理由、四层指标、判定、失败层、样本文档与回答等 23 个字段）。
前端 `GET /api/attacks/iterations` 读这张表，所以：

- **刷新页面不会丢轨迹**（不是内存态）；
- 点"刷新轨迹"能看到**正在跑**的战役已经完成的轮次。

### （3）策略清单与防御档清单是后端给的

`GET /api/attacks/strategies` 与 `/variants` 直接把后端的注册表返回给前端渲染，
所以**界面上显示的策略永远是代码里真实存在的那几个**，不会出现"文档写了但没实现"。
防御档的说明文字也在后端：

```python
notes = {
    exp.VARIANT_NAIVE:      "裸 RAG：检索后直接生成，无任何核查（对照组）",
    exp.VARIANT_FIXED:      "原固定链路：retrieve → grade → generate",
    exp.VARIANT_AGENT_STAT: "Agent + 旧统计检测器（消融对照，召回率 0%）",
    exp.VARIANT_AGENT:      "Agent + 新混合检测器（规则 + LLM 语义判定）",
}
```

### （4）柱状图为什么不用 echarts

只用 CSS 高度百分比画柱，`barHeight(v)` 做一次归一化（clamp 到 0–1，
最小 3% 保证"零值也看得见"）。详见[第六节](#六前端工程与实现细节)。

|---|---|---|

## 完成了什么

4. 勾选两个以上实验 → **一键对比平均指标**（柱状图 + 表格）。

## 怎么做到的

### （1）后台执行：接口立刻返回，线程池里跑

实验动辄几分钟，所以 `POST /api/experiments?auto_start=true` 只负责建记录 + 起线程：

```python
def start_experiment_async(experiment_id) -> bool:
    ...
    with _lock:
        if experiment_id in _running_ids:
            return False            # 防重复启动
        _running_ids.add(experiment_id)
    threading.Thread(target=_run_experiment, args=(experiment_id,), daemon=True).start()
    return True
```

`_run_experiment()` 把状态从 `pending` → `running` → `completed`/`failed` 写进库，
异常会记进 `error_message`（前端能看到失败原因，而不是"悄悄没了"）。

### （2）状态轮询：会自动停

前端每 5 秒拉一次列表，**发现没有 `running` 的实验就自己停掉定时器**：

```js
pollTimer = setInterval(async () => {
  await loadList()
  if (!experiments.value.some((e) => e.status === 'running')) {
    clearInterval(pollTimer); pollTimer = null      // 避免无意义请求
  }
}, 5000)
```

并且在 `onBeforeUnmount` 里 `clearInterval`——**离开页面必须清定时器**，
否则会一直空转（这是本项目修过的一个真实问题）。

### （3）对比：后端做聚合，前端只渲染

`POST /api/experiments/compare` 接收实验 ID 列表，后端把每个实验的所有结果行
按指标名分组求平均：

```python
for k, v in r.metrics.items():
    if isinstance(v, (int, float)):
        agg.setdefault(k, []).append(float(v))
averages = {k: round(sum(v) / len(v), 4) for k, v in agg.items() if v}
```

前端 `compareMetrics` / `compareRows` 再把结果转成 `MetricBars` 需要的形状
（指标定义 + 数据行），**指标种类由数据自动决定**，不需要前端硬编码。

下面那条蓝色提示很关键，它说明了**这个页面与"注入向量库"是两回事**——

## 能做什么

1. **批量生成**投毒文档并入库（供实验与检测器复用，不必每次重新生成）；
2. **按场景清空**，一键清理某个攻击目标的全部投毒文档；
3. 逐条**删除**；
4. **看检测结论**，直观对比"哪批投毒能被检测器抓住、哪批抓不住"。

## 怎么做到的

### （1）生成复用了实验侧的模板生成器

`poison_doc_service.generate_and_save()` 直接调用
`RAGblack._generate_poison_variants()`——**纯 Python，不依赖 Ollama**，
所以这个页面在没有本地模型的情况下也能用：

```python
task = exp.ATTACK_PAIRS[attack_index]
variants = exp._generate_poison_variants(task, count)
for content in variants:
    db.add(PoisonDocument(attack_index=..., domain=..., question=...,
                          target_answer=..., content=content,
                          keywords=task.get("keywords", [])))
```

**同一个生成器同时被三处复用**：这个页面、向量库注入（问答/实验）、
以及攻击 Agent 的 `template` 策略——保证"界面上看到的文档"与
"实验里注入的文档"是同一套东西。

### （2）`detected_poison` 这个字段曾被"设计过但没接通"

这个字段在表结构里、在响应 schema 里，但在早期版本中
**所有 Python 逻辑里从未被写入或读取**——是一个典型的"设计了但没接线"的死字段。
现在它被接到检测器上，界面上直接呈现三态。
（这个发现记录在 [`docs/agent诊断报告.md`](agent诊断报告.md) 第五节。）

### （3）删除有二次确认

`ElMessageBox.confirm` 包装删除操作，避免误点。按场景清空同样要确认，
因为一次会删掉几十篇。

## 路由与登录守卫

`router.js` 里的守卫逻辑回答了三个问题：

```js
router.beforeEach(async (to) => {
  if (!authState.checked) await fetchMe()      // ① 首次导航先问后端"我登录了吗"
  if (to.meta.public) return authState.user ? { path: '/chat' } : true   // ② 已登录别看登录页
  if (!authState.user) return { name: 'login', query: { redirect: to.fullPath } }  // ③ 未登录跳登录并记住目标
  return true
})
```

**为什么必须问后端**：会话在 HttpOnly Cookie 里，**前端读不到**，
所以只能调 `/api/auth/me` 确认。这既是安全设计（防 XSS 窃取），
也决定了"刷新页面时先闪一下"是不可避免的。

## 会话失效的统一处理

`api.js` 拦截所有响应，遇到 **401 且 code 是 `session_expired` / `unauthenticated`**
就广播一个自定义事件，由上层统一跳登录页——而不是在每个页面里各写一遍：

```js
if (status === 401 && (data?.code === 'session_expired' || data?.code === 'unauthenticated')) {
  emitUnauthorized({ code: data.code })
}
```

## API 客户端：两套通道

| 通道 | 用途 | 实现 |
|---|---|---|
| axios 实例 | 普通请求 | `baseURL: '/api'`、`withCredentials: true`（带上 HttpOnly Cookie）、120s 超时、响应拦截直接返回 `resp.data` |
| `fetch` + ReadableStream | **SSE 流式** | `sseStream()` 自己逐帧解析 `event:` / `data:`，因为 axios 不适合处理流 |

## 性能处理

| 措施 | 效果 |
|---|---|
| **移除 echarts** | 它只为画一处柱状图，却把约 1MB 图表库打进包；换成纯 CSS 的 `MetricBars.vue` 后 `ExperimentsView` 从 **1040KB → 7.3KB** |
| **路由懒加载** | 所有页面都用 `() => import(...)`，首屏只加载登录页，其余按需拉取 |
| **vendor 分包** | `vite.config.js` 把 element-plus / vue / axios 拆成独立 chunk，业务代码改动后用户不必重新下载整个 vendor |
| **轮询自动停止** | 实验列表没有 running 实验时立即清掉定时器；离开页面也清 |
| **vendor-element 仍偏大** | 942KB（gzip 297KB），后续可改 Element Plus 按需引入进一步优化 |

## 视觉一致性

`styles/global.css` 用 CSS 变量统一了配色、圆角、阴影与文字层级
（`--brand` / `--text-1/2/3` / `--border` / `--shadow-sm` / `--bg-page` 等），
所以各页面虽然是分开开发的，观感一致。语义色约定贯穿全站：

| 颜色 | 含义 |
|---|---|
| 🔴 红 / 危险 | 投毒、攻击成功、出错、删除类操作 |
| 🟢 绿 / 成功 | 检测到、防御生效、ASR 失败、完成 |
| 🟡 黄 / 警告 | 待评估、需要谨慎（如 Agent 拒答提示） |
| 🔵 蓝 / 信息 | 中立提示、参数说明 |
| ⚪ 灰 | 无数据、未启用 |

# 一句话总结

**四个部分对应一条完整的研究动线：**

> **投毒文档**（准备弹药）→ **问答演示**（看 Agent 如何被攻击、如何防御）→
> **攻防对抗**（让攻击自适应迭代，看防御在哪一层失守）→
> **实验管理**（把结果量化、对比、沉淀）。

前端的价值不只是"能操作"，而是把原本看不见的东西变成**看得见**：
模型的**决策过程**、攻击的**策略演化**、防御的**失效层**、证据的**可信度**。
